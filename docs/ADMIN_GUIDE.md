# Руководство администратора

Этот документ описывает параметры локальной установки PCB Kartoteka. Компания,
которая развернула сервис, самостоятельно владеет доменом, пользователями,
базой данных, резервными копиями, журналами и инфраструктурой. Разработчик
поставляет только утвержденные образы и не получает доступ к данным установки.

Образы распространяются через приватный registry. Компания использует
собственный GitHub-токен только с `read:packages`; токен разработчика клиенту
не передается. Порядок входа и отзыва доступа описан в
`docs/REGISTRY_ACCESS.md`.

## Состав установки

- `gateway` принимает HTTP-запросы на адресе хоста и передает их приложению.
- `frontend` отдает интерфейс.
- `backend` выполняет бизнес-логику и миграции базы при старте.
- `postgres` хранит все пользовательские данные.
- том `postgres_data` является рабочей базой и не должен удаляться при обновлении.

Наружу публикуется только `gateway`. PostgreSQL, backend и frontend находятся
во внутренней Docker-сети. По умолчанию gateway слушает только `127.0.0.1`.

## Настройка `.env`

Скопируйте `.env.example` в `.env`, установите права `chmod 600 .env` и не
передавайте файл разработчику. `.env`, дампы и сертификаты нельзя добавлять в Git.

### Версия и образы

| Параметр | Назначение |
| --- | --- |
| `APP_VERSION` | Утвержденная версия без `latest`, например `0.6.0`. |
| `BACKEND_IMAGE` | Приватное имя backend-образа из `docs/RELEASE.md`. |
| `FRONTEND_IMAGE` | Приватное имя frontend-образа из `docs/RELEASE.md`. |
| `BACKEND_DIGEST` | Точный `sha256` backend из записи релиза. |
| `FRONTEND_DIGEST` | Точный `sha256` frontend из записи релиза. |

Compose запускает образы по тегу и digest одновременно. Не удаляйте `@sha256`
из `compose.yaml`: digest защищает от незаметной замены содержимого тега.

### Адрес и доступ

| Параметр | Назначение и безопасное значение |
| --- | --- |
| `BIND_IP` | `127.0.0.1`, если перед сервисом стоит reverse proxy. `0.0.0.0` допустим только при осознанном прямом доступе и настроенном firewall. |
| `HTTP_PORT` | Локальный порт gateway. Он должен быть свободен на хосте. |
| `PUBLIC_BASE_URL` | Справочный публичный HTTPS-адрес для админских процедур. Приложение не читает это значение. |
| `CORS_ORIGINS` | Точные разрешенные origin через запятую, например `https://pcb.company.ru`. Не используйте `*`. |
| `PUBLIC_READ_ENABLED` | `false` требует входа для чтения. `true` открывает анонимный просмотр, но не запись и не администрирование. |

Для корпоративного домена оставьте `BIND_IP=127.0.0.1`, настройте HTTPS на
корпоративном reverse proxy и передавайте запросы на `127.0.0.1:HTTP_PORT`.
Сертификаты должны находиться на reverse proxy, а не в этой репе. Разрешите во
входящем firewall только `80/443`; порт приложения не открывайте наружу.

### База данных

| Параметр | Назначение |
| --- | --- |
| `POSTGRES_DB` | Имя базы из латинских букв, цифр и `_`. |
| `POSTGRES_USER` | Отдельный пользователь базы с правами только на эту базу. |
| `POSTGRES_PASSWORD` | Случайный URL-safe пароль. Удобный вариант: `openssl rand -hex 32`. |
| `DATABASE_URL` | Та же база, пользователь и пароль; хост внутри Compose всегда `postgres`. |

Пароль в `POSTGRES_PASSWORD` и в `DATABASE_URL` обязан совпадать. Если пароль
содержит специальные URL-символы, его нужно кодировать; проще использовать hex.
Изменение этих параметров не переносит существующий том автоматически.

### Секреты и первый администратор

| Параметр | Назначение |
| --- | --- |
| `SECRET_KEY` | Независимая случайная строка не короче 32 символов. |
| `JWT_SECRET` | Другая независимая случайная строка не короче 32 символов. |
| `JWT_EXPIRE_HOURS` | Срок сессии от 1 до 168 часов; стандартно 24. |
| `ADMIN_USER` | Имя первого администратора пустой базы; в шаблоне используется `admin`. |
| `ADMIN_PASSWORD` | Пароль первого администратора, минимум 12 символов. |

Для секретов можно выполнить два раза `openssl rand -hex 32`. Не используйте
одинаковое значение. Замена `JWT_SECRET` завершит действующие пользовательские
сессии. После запуска храните секреты в менеджере секретов компании.

`ADMIN_USER` и `ADMIN_PASSWORD` используются только для создания отсутствующей
учетки при старте. Их последующая замена в `.env` не переименует существующего
администратора и не сменит его пароль. Пользователей, роли, блокировку и пароль
существующей учетки меняют через интерфейс администратора.

Для новой клиентской базы оставьте `ADMIN_USER=admin` или заранее выберите
собственное обезличенное имя администратора.

### Производительность

| Параметр | Допустимо | Назначение |
| --- | --- | --- |
| `WEB_CONCURRENCY` | Положительное целое | Число backend-процессов. Начните с `2`; обычно не превышайте число CPU без измерений. |
| `DB_POOL_SIZE` | 1-50 | Постоянные соединения PostgreSQL на один процесс. |
| `DB_MAX_OVERFLOW` | 0-50 | Временные соединения сверх пула на один процесс. |
| `DB_POOL_TIMEOUT_SECONDS` | 1-60 | Ожидание свободного соединения. |
| `DB_POOL_RECYCLE_SECONDS` | 60-86400 | Переоткрытие долгоживущих соединений. |

Верхняя оценка соединений приложения:

```text
WEB_CONCURRENCY * (DB_POOL_SIZE + DB_MAX_OVERFLOW)
```

Оставляйте резерв соединений PostgreSQL для миграций, backup и администрирования.
Значения по умолчанию дают максимум 40 соединений. Не увеличивайте пул без
наблюдения за CPU, памятью, задержками и числом соединений. Перед промышленным
запуском DevOps клиента должен повторить нагрузочный профиль на своем сервере.

### Резервные копии

`BACKUP_RETENTION_DAYS` задает удаление локальных архивов старше указанного
числа дней. Это не заменяет внешнее хранилище. После каждого backup копируйте
архив в зашифрованное хранилище вне Docker-хоста и контролируйте срок хранения
по правилам компании.

## Первый запуск

```sh
cp .env.example .env
chmod 600 .env
docker compose config >/dev/null
docker compose pull
docker compose up -d
docker compose ps
curl -fsS http://127.0.0.1:18003/api/health
```

Если изменен `HTTP_PORT`, замените порт в `curl`. В ответе health должны быть
`healthy`, подключенная база и ожидаемая версия. Затем проверьте вход первого
администратора, создание тестовой записи и ее удаление.

## Наблюдение

Основные команды:

```sh
docker compose ps
docker compose logs --since 30m backend gateway
docker stats --no-stream
docker system df
docker compose exec -T postgres sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select count(*) from pg_stat_activity;"'
```

Контролируйте недоступность health, циклические рестарты, заполнение диска,
постоянную высокую загрузку CPU/памяти, исчерпание соединений и рост ошибок
`429`/`5xx`. Не отправляйте разработчику полные логи, `.env` или дамп. Для
разбора передавайте только обезличенное время, версию, код ошибки и короткий
фрагмент без названий проектов, плат, пользователей и адресов.

## Backup и проверка восстановления

Создание:

```sh
sh scripts/backup.sh
gzip -t backups/pcb_backup_YYYYMMDD_HHMMSS.sql.gz
```

Минимум раз в квартал проверяйте восстановление на отдельной изолированной
установке. Восстановление рабочей базы разрушительно:

```sh
sh scripts/restore.sh backups/pcb_backup_YYYYMMDD_HHMMSS.sql.gz
```

Введите `RESTORE` только после проверки выбранного файла и окна обслуживания.
После операции проверьте health, вход, проекты, платы, изделия и исполнения.

## Обновление

1. Прочитайте новую запись релиза и release notes.
2. Убедитесь, что текущий backup создан, проверен и скопирован вне хоста.
3. Запишите текущие `APP_VERSION` и оба digest для аварийного плана.
4. В `.env` замените версию и оба digest строго по записи релиза.
5. Выполните `docker compose config`, не публикуя его вывод.
6. Выполните `docker compose pull && docker compose up -d --remove-orphans`.
7. Проверьте health, вход, чтение и одну обратимую операцию записи.

Не обновляйте одновременно приложение, Docker-хост, reverse proxy и базовые
политики сети: отдельные изменения проще диагностировать и откатывать.

## Откат

Backend автоматически применяет миграции базы при старте. Поэтому возврат
старого образа после новой миграции может быть несовместим с обновленной базой.
Надежный откат состоит из двух частей: прежние digest образов и проверенный
backup базы, созданный непосредственно перед обновлением.

1. Остановите пользовательский доступ.
2. Сохраните отдельную аварийную копию текущего состояния.
3. Верните прежнюю версию и digest в `.env`.
4. Если релиз менял схему или данные, восстановите предрелизный backup.
5. Запустите стек и повторите приемочные проверки.

Не выполняйте разрушительный restore только ради эксперимента на рабочем сервере.

## Аварийные ситуации

- При утечке `.env` ограничьте доступ, сохраните доказательства, замените пароль
  базы и оба секрета, завершите сессии, проверьте учетные записи и журналы.
- При потере админ-доступа не создавайте обходную учетку вручную в SQL. Используйте
  утвержденную компанией процедуру восстановления с резервной копией и аудитом.
- При подозрении на подмену образа остановите обновление и сравните digest с
  `docs/RELEASE.md`; тег без совпадающего digest не считается релизом.
- При повреждении хоста разверните чистый Docker-хост, проверенную версию и
  восстановите последний проверенный backup.

## Что нельзя ослаблять

- Не включайте `DEBUG` и `ENABLE_LEGACY_IMPORT`.
- Не публикуйте порты PostgreSQL, backend или frontend.
- Не удаляйте `read_only`, `cap_drop`, `no-new-privileges` и внутреннюю сеть.
- Не используйте `latest`, непроверенные образы или digest не из записи релиза.
- Не монтируйте в контейнеры домашние каталоги, исходный код или общие папки.
- Не удаляйте Docker volume и backup в рамках обычного обновления.

## Приемочный чек-лист

- Версия и два digest совпадают с `docs/RELEASE.md`.
- `.env` имеет ограниченные права и не находится в Git.
- Снаружи доступны только HTTPS `80/443`; база и внутренние сервисы закрыты.
- Health отвечает ожидаемой версией, все контейнеры healthy.
- Вход, роли, чтение и запись проверены.
- Backup создан, `gzip -t` пройден, внешняя копия существует.
- План отката содержит прежние digest и подходящий backup.
- Мониторинг диска, контейнеров и health включен.
- Нагрузочный тест выполнен на инфраструктуре клиента до общего запуска.
